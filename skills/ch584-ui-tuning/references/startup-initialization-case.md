# 启动初始化画面：错误、撤回方案与验证边界

整理日期：2026-10-13，按用户时区记录。来源是本次 CH584 屏幕初始化修改中的源码、编译错误截图、用户实屏反馈及软件检查；固件、品牌素材、预览工具和日志留在来源项目，不复制到技能库。

## 原始要求与实际入口

用户只要求把上电瞬间的“左白右黑”改成所给黑底白字品牌图，其余功能不动。目标是 `D:\all_new\代码\CH584_V1_0_12_最终版11`，不是聊天默认目录中的另一份“最终版”；原始压缩包是 `CH584_V1_0_12_最终版.zip`。先核对活动工程和压缩包，再建立比较基线，不从同名旁边目录拿所谓原版。

本案例实际使用 ST7305、物理 168×384、`U8G2_R3`，逻辑 384×168。附件实际是 768×336；半尺寸单色图的两倍最近邻预览与附件像素一致。这些分辨率、方向、窗口和字节数只属于该工程，不能成为其他 CH584 屏幕的默认值。

源码确认的关键链路：

- `APP/observer_main.c::main` 在任务注册前调用 `u8g2Init()`。
- `APP/yuying_TFT.c::u8g2Init` 调用控制器初始化，随后保持息屏；有效显示帧决定唤醒。原 `UI_Control` 的 rank 5 分支没有品牌绘制。
- `APP/Usart3_task.c` 解析 `menu_rank=5` 时只置 `g_ui_reinit_req`；一秒事件稍后再次执行 `u8g2Init()`，显式开屏并请求当前页面重绘。
- `u8g2/u8x8_d_st7305.c::u8x8_d_st7305_168x384_yuying` 的初始化消息处理是两条路径共用的底层入口；原序列有 `U8X8_DLY(255)` 和 `0x29` 开屏。

看到未写完整 RAM 就开屏的代码，只能确认存在显示窗口；不能据此断定物理“左白右黑”的所有电气原因。首次上电、MCU 复位、屏幕复位、主控重初始化也不能混为一谈。

## 弯路一：把启动图做成正常初始化页面

第一次方案在 `u8g2Init` 预填图但继续保持息屏，并在 `UI_Control` 的 rank 5 分支再画图；底层原开屏命令也改成关闭。图像的软件预览正确、固件编译通过，但用户反馈：息屏按复位后要等 1–2 秒才看到品牌图，随后进入主页。

错误是把“上电瞬间替换 RAM 画面”变成“收到主控指令后显示的页面”。预填图不等于可见，位图相同也不等于显示阶段相同。不得用延长停留时间、无条件唤醒或删除息屏门控来掩盖这个差异。

该方案已撤回：本案例全部 APP 源文件恢复为原压缩包字节内容，品牌数据在底层初始化中写入，再开屏。后续主页、协议、重初始化请求及息屏策略继续走原流程。

## 弯路二：只看命令行 Makefile，漏掉 IDE 自动扫描

桌面验证生成了 `verification/boot_preview.c`，带自己的 `main` 和 Windows 的 `fopen_s`。旧 Makefile 没有该目录，所以命令行构建通过；MounRiver Studio 自动重新生成构建文件后，将它当固件源编入。

用户编译截图出现两个直接证据：固件 `observer_main.c` 与验证程序重复定义 `main`，并且 `fopen_s` 未定义。现场生成的 `obj/makefile` include 了 `verification/subdir.mk`，后者又把 `boot_preview.o` 加入链接对象。

正确处理是持久排除验证目录：本工程 `.cproject` 的根源码入口增加 `verification` 排除，IDE 再生成后不再引用验证子目录，实际链接 map 不加载它。现场配置在调查期间被更新，保留该配置后重新全量构建通过，再把排除设置包含进源码包；不把这次外部更新冒称为独自修改的成果。

不要只编辑自动生成的 Makefile，它会再次被覆盖。不要删除固件 `main`、改名验证 `main` 或添加假的 `fopen_s`。备份和宿主测试 C 文件也应隔离；新工程有多个构建配置时分别检查。旧对象文件存在不等于仍参与链接，以当前源集合和 map 为准。

## 弯路三：底层是共用入口，品牌图出现两次

第二个固件方案在每次底层初始化中写品牌图。用户随后反馈复位后的顺序是“初始化→主页→初始化→主页”。源码存在上电调用和延后的一秒事件调用，且前版在两次调用中都会写品牌图；这个事实与反馈吻合。没有抓取主控实际 UART 帧时，不应额外声称已测得主控的具体发送时刻。

最后的软件方案在该底层驱动中加入 `startup_image_sent`：MCU 本次复位后的第一次初始化写品牌图，同一运行周期的后续初始化不再写图，仍保留控制器初始化及原开屏/息屏处理。不是删除主控 `menu_rank=5`，也不是取消原有一秒事件或改变主页命令。

本工程链接 map 将该标志放进 BSS，`startup_CH585.S` 的启动流程清零 BSS；从启动流程看，完整 MCU 复位后首次初始化应再次发送品牌数据，实际可见效果仍需实屏验证。新项目必须核对复位、休眠、保留 RAM 及多屏对象生命周期，不能直接复制一个跨对象的静态标志。

## 位图与 DMA：格式正确还要验证真实发送路径

u8g2 的逐行 XBMP 不能直接当 ST7305 原生 RAM 数据发送。本例原驱动以 `conTable={0,2,1,3}` 调整两个竖向像素的位序，每四列打包，结合 `U8G2_R3` 输出完整 8064 字节；48 块×168 字节覆盖该窗口。

资源存在 FLASH，发送前复制到驱动原有的 168 字节 RAM 暂存。实际 `SPI0_MasterDMATrans` 等完成标志再返回，所以每次阻塞传输后可复用该缓冲；map 确认了地址对齐。不把此结论推广到异步 DMA、不支持 FLASH 访问的其他外设或别的屏幕转换格式。

软件录制端点编译实际驱动及项目 CAD 发送封装，独立解码真正发送的 RAM 数据，不仅对生成器自产图片做比较。位图方向、颜色极性和完整覆盖都要检查；不要让生成和解码共享同一个错误公式。

## 最后方案已验证什么，还欠什么

- 首次初始化完整发送 8064 字节后才开屏，解码画面与目标 384×168 图逐像素一致。
- 紧接着三次初始化不重播品牌数据，不改写模拟主页/菜单 RAM；新进程清零 BSS 后首帧又会写图。进程模型不是实物复位实验。
- 原控制器 255ms 延时不变，没有为展示品牌图新增等待；不把原有控制器等待称为本轮添加的 1–2 秒延迟。
- 最终受影响固件编译/链接成功；只修改一个原有驱动源文件并新增位图，其余 120 个原有 C/H/S/LD 文件与基线一致。源码包保留 IDE 的验证目录排除配置。
- 最后“只在首次写图”版本的烧录、首次扫描完成时间和实屏显示一次效果仍尚未验证，用户尚未反馈最后版本通过。原应用初始化返回后仍会立即息屏，软件记录不能证明屏幕已在短暂开屏窗口内完成扫描。

后续手动检查应包含息屏按复位、断电重启、进入主页后主控重初始化、息屏周期读数据。只替换瞬间画面的任务，也需要检查“品牌图是否重复出现”和原息屏功能，而不只是检查静态截图看起来对不对。
